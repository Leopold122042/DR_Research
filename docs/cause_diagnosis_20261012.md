# 冻结状态的电费差距诊断

本实验定位当前候选评价 GNN 的电费差距来自哪里：候选覆盖、续接验收，还是评分排序及前 8 个尝试限制。它读取已完成的一周实验，在选定状态上做离线核验；不训练模型，不重新运行一周闭环控制。

默认配置为 `configs/cause_diagnosis.toml`，入口为 `scripts/diagnose_control_gap.py`。所有计算由用户在本地启动，诊断结果保存在新的目录中。

## 固定实验口径

| 项目 | 设置 |
|---|---|
| 系统规模 | S2：32×8×4；S3：128×32×16；S4：512×128×64，顺序为热泵×储罐×建筑 |
| 状态来源 | `artifacts/rerun_20261009_194453` 中 GNN 实际轨迹 |
| 模型 | `artifacts/full_20261009/hpo/selected.pt`，冻结现有权重 |
| 快照 | 每个规模 4 个，共 12 个；根据时段、电价和种子 42 预先选择 |
| 候选 | 同一 Sobol 序列前缀 64、256，各加备用动作；去重后实际数量可能减少 |
| 窗口 | 48 个半小时时段，即 24 小时；到达周末终点时缩短 |
| LP 核验 | 固定完整当期动作，优化窗口后续动作；采用原实验求解方法，默认单线程、每次 120 秒上限 |
| 边界与约束 | 共享库存、上一时刻功率、需求、电价及物理约束；共享终端库存，非周末终点窗口还共享末步功率衔接条件 |

抽样过程不读取电费差距、回退次数或模型分数。当前归档的实际选择如下，程序会检查各规模的时刻一致性：

| 背景 | 时刻索引 t（从 0 开始） | 时间 | 每个规模对应的快照 ID |
|---|---:|---|---|
| 工作日谷价、临近涨价 | 11 | 周一 05:30 | `S2_t011`、`S3_t011`、`S4_t011` |
| 工作日最高电价 | 183 | 周四 19:30 | `S2_t183`、`S3_t183`、`S4_t183` |
| 周末白天 | 311 | 周日 11:30 | `S2_t311`、`S3_t311`、`S4_t311` |
| 周日末段 | 331 | 周日 21:30 | `S2_t331`、`S3_t331`、`S4_t331` |

周日末段窗口较短，分析时需要结合窗口长度，重点比较同一快照内各方法的差距。12 个快照用于定位机制，不代表所有时刻的统计结论。

## 核验值和六个比对组

对状态 t 的当期动作 a，定义：

\[
Q_t(a)=\min_{\text{窗口后续动作}}\left(\text{当期电费}+\text{窗口后续电费}\right),
\qquad \text{当期动作固定为 }a.
\]

动作 a 同时包含全部热泵功率和储罐到建筑的供热量。Q 是相同物理模型、预测窗口及终端条件下的 LP 最优值，单位为元；它不是 GNN 预测分数，也不是后续实际执行轨迹的累计电费。离线 LP 时间单独记录，不加入 GNN 在线控制时间。

| 组别 | 选择方式 | 回答的问题 |
|---|---|---|
| A：连续 LP | 当期动作也由 LP 优化，得到 Q* | 当前模型下的共同窗口基准 |
| B：候选池理想选择 | 在全池 LP 可行候选中按 Q 选最优，得到 Q_F | 候选池本身有没有好动作 |
| C：现有验收下的理想选择 | 对全池逐个调用现有续接器，在通过者中按 Q 选最优，得到 Q_A | 续接器遗漏了多少可行且低成本的机会 |
| D：完整 GNN 排序 | 按完整 GNN 分数排序，选择首个通过现有验收的候选，不限尝试次数 | 完整模型的排序质量 |
| E：自适应 GNN 排序 | 按归档自适应评分排序，选择首个通过验收的候选，不限尝试次数 | 消息精化对排序的影响 |
| F：原控制流程 | 自适应评分、最多尝试前 8 个、必要时回退备用动作，得到 Q_exec | 原实验实际执行决策 |

原 256 候选池上，完整的原因分解为：

\[
Q_{\mathrm{exec}}-Q^*
=\underbrace{Q_F-Q^*}_{\text{候选覆盖}}
+\underbrace{Q_A-Q_F}_{\text{续接验收遗漏}}
+\underbrace{Q_{\mathrm{exec}}-Q_A}_{\text{排序与尝试限制}}.
\]

三项在相同约束口径下非负，程序检查加和恒等式及数值容差。排序部分继续报告 D−C、E−D、F−E：依次对应完整模型排序、消息保真机制的改变、前 8 个限制及备用回退。后两项允许为负；例如备用动作可能比沿排序继续验收得到的动作更便宜。

64 候选结果只报告覆盖质量，不把 256 池中的评分子集伪装成独立运行的 64 候选控制器。可选 1024 候选扩展同样只用于覆盖分析，不重新调度消息精化。

另求解一次“当期总功率限制在生成器区间内”的 LP。其最优值减去 Q* 是功率区间限制的代价；候选最优值再减去该最优值，是区间内采样及其他动作映射限制的合计代价。第二项仍不能全部解释成候选数量不足。

## 如何复现原决策

快照从原始构造备用计划出发，依次用过去已经执行的动作重建续接计划，核对库存、上一时刻功率和终端衔接。归档未来的实际动作是后续决策的结果，不用于替代当前备用计划。

自适应评分按归档的精化位置和顺序回放。这样每次启动诊断都沿用原来的消息精化决策，不受当前机器瞬时速度影响。程序独立计算完整 GNN 分数，并检查原首选候选、实际执行动作及前 8 个验收结果能否复现。

`diagnostic_score_times` 是共享准备及缓存的诊断回放耗时；历史在线控制耗时另存。二者用途不同，本实验不据此给完整 GNN 和自适应 GNN做在线速度排名。

程序核对归档协议、场景、模型和原控制内核的哈希。输入或诊断代码发生变化时，原输出目录的续跑会停止并提示使用新目录，防止不同版本的标签混用。

## 本地运行

在 PowerShell 中进入仓库。下列命令使用已有虚拟环境及默认归档路径。

```powershell
Set-Location 'C:\Users\10632\Documents\GitHub\DR_Research'
```

**一次完成 S2、S3、S4 全部诊断：**

```powershell
& .\.venv\Scripts\python.exe .\scripts\diagnose_control_gap.py --out .\artifacts\cause_diagnosis_20261012
```

首次运行先准备快照和评分，再生成 LP 标签。已有目录会自动跳过已经完成的快照和标签。中断后重复同一条命令即可续跑；完成的标签逐个落盘。

**只准备和核对快照，不执行 LP 核验：**

```powershell
& .\.venv\Scripts\python.exe .\scripts\diagnose_control_gap.py --out .\artifacts\cause_diagnosis_20261012 --prepare-only
```

**先运行 20 次新 LP 求解，观察本机耗时：**

```powershell
& .\.venv\Scripts\python.exe .\scripts\diagnose_control_gap.py --out .\artifacts\cause_diagnosis_20261012 --max-solves 20
```

`--max-solves` 限制本次进程新增的 LP 次数，包括连续基准、功率区间基准和候选标签。它不限制快照准备。默认从 S2 开始，S2 的耗时不能直接外推 S4。若先测 S4，可运行：

```powershell
& .\.venv\Scripts\python.exe .\scripts\diagnose_control_gap.py --out .\artifacts\cause_diagnosis_20261012 --snapshots S4_t011 --max-solves 10
```

完成试跑后使用不带 `--max-solves`、不带 `--snapshots` 的全量命令，继续其余工作。

**重试超时或未判定标签，并将单次上限提高到 300 秒：**

```powershell
& .\.venv\Scripts\python.exe .\scripts\diagnose_control_gap.py --out .\artifacts\cause_diagnosis_20261012 --retry-unknown --solver-time-limit 300
```

正常续跑会保留已经记录的未判定结果；`--retry-unknown` 才会重新求解它们。最优和已证明不可行的标签始终复用。此处的命令行时间上限只影响离线求解，不改变优化问题，也不改变归档控制器设置。

**只重新汇总已有标签：**

```powershell
& .\.venv\Scripts\python.exe .\scripts\diagnose_control_gap.py --out .\artifacts\cause_diagnosis_20261012 --summarize-only
```

**在发现覆盖问题后，定向扩展到 1024 个候选：**

例如，仅扩展 S4 周四高价快照：

```powershell
& .\.venv\Scripts\python.exe .\scripts\diagnose_control_gap.py --out .\artifacts\cause_diagnosis_20261012 --snapshots S4_t183 --extend-count 1024
```

可在 `--snapshots` 后列出多个 `snapshot_index.json` 中的 ID。扩展复用原有动作及 LP 标签，并检查前缀动作哈希一致；只对新增动作补标签。扩展与重试可以继续使用相同输出目录。

如归档或模型位于其他路径，可显式传入 `--source`、`--checkpoint`；它们仍必须匹配同一次原实验。修改 `configs/cause_diagnosis.toml` 中的实验配置后，使用新的 `--out` 目录。相同目录一次只运行一个诊断进程。

## 计算量、状态和结果文件

初始上限约为 12×(257+2)=3108 次 LP：每个快照最多 257 个含备用候选，再加两个基准。候选去重和断点复用会减少新增求解次数。64 候选结果复用前缀标签，不另做一套 LP。1024 扩展每个选定快照最多再增加 768 个标签。

运行日志报告当前快照、标签状态、单次耗时和最近同快照求解耗时的中位数。冷启动、规模、终端约束和求解难度会改变时间；试跑数据提供本机量级参考，不保证整轮完成时间。

LP 标签分为 `optimal`、`infeasible`、`unknown`。超时或数值失败属于 `unknown`，不作为不可行。存在未判定标签时，程序保留“目前已知最好候选”，并暂停给出完整候选池的精确最优及三项分解。原执行无法复现时也不生成有效归因。

| 文件 | 内容 |
|---|---|
| `diagnosis_manifest.json` | 输入、配置、诊断代码哈希，保证续跑一致 |
| `snapshot_index.json` | 快照 ID、时段类别、时间、电价 |
| `candidate_labels.csv` | 每个候选的 LP 状态、电费、验收结果、两类 GNN 分数 |
| `snapshot_summary.csv` | 各快照、各候选数量的覆盖及三项分解，含排序细分 |
| `summary.json` | 完整汇总、完成状态、各组动作 ID 和核验值、金额归一化结果 |
| `snapshots/<ID>/snapshot.json` | 固定动作池、续接结果、归档精化信息及耗时来源 |
| `snapshots/<ID>/arrays_256.npz` | 冻结的状态、备用计划和候选动作；扩展另存对应数量的文件 |
| `snapshots/<ID>/labels/` | 每次 LP 的独立记录、状态、统计和重试历史 |

运行后优先提供 `summary.json`、`snapshot_summary.csv` 和 `candidate_labels.csv` 进行分析；若发生一致性错误，再提供完整日志及对应快照文件。

分析先看三项差距的金额、元/储罐和相对连续 LP 的百分比，再看 64→256 的覆盖改善及 D/E/F 差异。完整标签的 `complete` 表示该诊断口径下核验完成，不表示已经找到真实系统的最优控制。

这些数值是冻结状态下、窗口后续动作可以重新优化时的决策差距。窗口之间重叠，真实闭环后续状态也会改变，因此不能把快照金额相加当作一周电费差额的精确分账。下一步改进方向应结合各规模、各背景的一致性确定。
